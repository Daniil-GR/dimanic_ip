# dimanic_ip — MTProto Monitor

## Локальный сайт (режим по умолчанию)

Windows: `py -3 -m pip install -r requirements.txt`, затем ` .\check-proxy.cmd` (без начального пробела). Linux: установите зависимости в venv и выполните `bash check-proxy.sh`.

Откроется http://127.0.0.1:8765. В браузере можно сохранить/заменить API-ключ, вставить MTProto-ссылку, запустить проверку всех A-записей, следить за прогрессом, повторить отдельный IP или проблемные IP, фильтровать таблицу, смотреть интерактивную топологию и скачать CSV/JSON. Повтор всех адресов с пустым полем использует последний сохранённый прокси. После завершённой проверки параметры ссылки сохраняются в `last_proxy.json` рядом с API-ключом (Windows: `%LOCALAPPDATA%\dinamic_ip`, Linux: `~/.config/dinamic_ip`). После перезапуска повтор отдельного IP и проблемных IP доступен, если ссылка соответствует последнему отчёту по идентификатору проверки. Для отчёта старой версии потребуется один раз заново ввести ссылку. Новый прокси заменяет сохранённый после завершения проверки. Файл содержит secret в открытом виде локально, на Linux создаётся с правами 0600; в отчёты, CSV/JSON и API состояния secret не включается. Чтобы забыть ссылку, остановите сайт и удалите `last_proxy.json`. Сервер слушает только loopback; для остановки Ctrl+C. Опции: `--port 8766`, `--no-browser`.

Отчёты сохраняются в папке `reports` рядом с локальным файлом API-ключа. Последний отчёт открывается после перезапуска. Отдельно отображаются RU/EXT и оригинальный статус API. RU data=true означает успех с российской точки. Повторные RU data=false дают REVIEW_DNS, а не доказательство блокировки; DNS не изменяется автоматически. При null нужна ручная диагностика. Консольный режим сохранён: `py -3 check_proxy.py` или `python3 check_proxy.py` (также `--cli` у обёрток).

## Справка по прежнему консольному режиму

# dimanic_ip — MTProto IPv4 checker

Проверяет каждый IPv4 из A-записей MTProto-домена через API RU + внешняя нода. Не изменяет DNS.

## Windows (PowerShell)

Установить Python 3.8+ с python.org. Для прямого запуска через `.sh` также установить Git for Windows.

```powershell
py -3 -m pip install -r requirements.txt
.\check-proxy.cmd --cli
```

В Git Bash: `bash check-proxy.sh --cli`. Если скрытый ввод в Git Bash не работает, использовать PowerShell и `.cmd`.

## Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
bash check-proxy.sh --cli
```

В Ubuntu при отсутствии venv: `sudo apt install python3-venv`.
Без dnspython скрипт работает через системный DNS, который может вернуть не все A-записи.

Ввести API-ключ (один раз) и ссылку `tg://proxy?server=proxy.example.com&port=443&secret=...` или `https://t.me/proxy?...`. Ввод скрыт. Один secret и порт должны действовать на всех IP этого домена. Для одиночной проверки можно передать IP в поле server ссылки.

## Управление ключом

- Linux / Git Bash: `bash check-proxy.sh --reset-key --key-only`
- Windows: `.\check-proxy.cmd --reset-key --key-only`
- Проверка сохранённого ключа: `--key-only`.

Перевыпуск ключа выполняется в боте: `/menu` → API-ключ → перевыпустить. Затем заменить его указанной командой. Новый ключ сохраняется только после успешного `/v1/me`.

Хранение: `%LOCALAPPDATA%\dinamic_ip\api_key` (Windows), `~/.config/dinamic_ip/api_key` (Linux). Это локальный текстовый файл, не шифрованное хранилище; на Linux права нового файла 0600. Не передавайте его третьим лицам. Ключ и secret не входят в CSV и не передаются в аргументах командной строки.

## Результаты

Скрипт последовательно проверяет адреса, выдерживая минимум 2.2 секунды между запросами. При 429 повторяет запрос с учётом Retry-After. RKN_BLOCK и DATA_CUT проверяются ещё раз. Только повторный подозрительный результат отмечается REVIEW_DNS. Это кандидат на ручную проверку и удаление A-записи, а не доказательство блокировки на всех операторах РФ. MT_DEAD/DOWN требуют диагностики VPS; ошибки API не считаются блокировками. `--no-recheck` отключает повтор. `--timeout 15` меняет таймаут API. CSV создаётся в текущей папке; `--output report.csv` задаёт путь.

С dnspython опрашиваются авторитетные NS зоны; при расхождениях берётся объединение ответов. При CNAME, сетевых ограничениях и динамических/географических DNS набор может быть неполным; сравнивайте его с панелью Dynadot.

API получает IP, порт и MTProto secret; убедитесь, что доверяете оператору сервиса. HTTP redirects не следуются. Проверка синхронная. API-схема основана на предоставленной документации.

## Dynadot DNS (REST v2)

В разделе Dynadot DNS укажите только Production API Key и Secret Key (или оба Sandbox-ключа и режим Sandbox). В Tools → API в Dynadot разрешите внешний IP устройства. Подключение проверяется чтением списка активных доменов через DOMAIN_LIST. Основной домен определяется автоматически по наиболее точному совпадению с именем прокси. При отсутствии совпадения изменения запрещены. Ключи сохраняются в `dynadot.json` рядом с локальным API-ключом MTProto, не в репозитории. Это локальный текстовый файл, не зашифрованное хранилище.

После завершённой проверки нажмите «Получить A-записи из Dynadot». Сопоставляются только точные A-записи проверенного поддомена автоматически найденной зоны. Выберите проверенные IP с RU data=false, подтвердите имя поддомена и удаление. Не удаляются рабочие или непроверенные IP, wildcard, другие поддомены и последняя A-запись. Удаление выполняется через REST REMOVE_DNS, не заменяет зону целиком. Предпросмотр действует 5 минут, зона читается повторно перед удалением. После операции сверяется полный набор записей и число удалений; при несоответствии не повторяйте запрос вслепую. Локальная резервная копия и результат в `dns-backups` рядом с ключами. Резервная копия не восстанавливается автоматически. Отчёт измерений остаётся историческим; выполните новую проверку после обновления DNS. Проверка RU не доказывает блокировку РКН. Без подтверждения пользователя DNS не меняется.

Документация: https://www.dynadot.com/domain/api-document?api-version=2.0.0#remove_dns . REST API может меняться; сначала проверьте в Sandbox на тестовой зоне. Реальные ключи и DNS не требуются для запуска MTProto-проверки.

### Диагностика HTTP 400

Первый DOMAIN_LIST выполняется без необязательных параметров; дополнительные страницы загружаются по pagination_result. При HTTP 400/401/403 во время подключения выполняется дополнительный подписанный запрос ACCOUNT_INFO (только чтение). Сообщение показывает метод, путь и идентификатор запроса, не выводя ключи или подпись. Проверьте, что используете пару Production API Key + Secret Key, и разрешите текущий внешний IP в Tools → API. Dynadot просит дать изменениям IP не менее 10 минут. Если ACCOUNT_INFO работает, а DOMAIN_LIST нет, это ошибка конкретного запроса списка доменов. Не передавайте ключи или заголовки авторизации в поддержку.

### Проверка X-Signature

При настройке сначала выполняется подписанный DOMAIN_LIST без необязательного X-Request-ID. Если Dynadot явно отвергает подпись, выполняется второй подписанный запрос с UUID. Используется только документированная формула HMAC-SHA256 с UTF-8 Secret Key и стандартным Base64. Успешный режим сохраняется вместе с ключами; при удалении DNS применяется только сохранённый режим. Запросы DELETE не повторяются автоматически с другой подписью. Если оба режима отклонены, проверьте пару Production API Key + Secret Key и обратитесь в Dynadot с диагностикой, не передавая ключи.

### Совместимость пагинации Dynadot

Поддерживаются boolean и строковые/числовые значения `has_next_page`, а также строковые числа `page`, `page_size`, `total`. Если ответ стандартного DOMAIN_LIST не содержит достаточной пагинации, выполняются явно нумерованные запросы `page` + `page_size=100`. Без метаданных завершение определяется только по пустой странице; повтор страниц, расхождение итогов или изменение списка между запросами блокируют управление DNS. Ключи, содержимое аккаунта и подписи не выводятся в диагностике.

### Диагностика GET_DNS

Запрос DNS выполняется для основного домена, найденного через DOMAIN_LIST, а не для имени прокси. Разбор ответа допускает регистр DNS/dns и плоский объект только при явном типе DNS и наличии обоих полных списков записей. Если формат неизвестен, ошибка показывает запрошенную зону и типы известных полей, без содержимого DNS, ключей или подписей. Внешние NS и неполные списки по-прежнему блокируют изменения.
